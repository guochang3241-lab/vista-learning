# VISTA 的设计与评估

## 项目想验证的主张

将学习围绕任务、卡点、最小实践和迁移来组织，是否能帮助学习者更快形成可用能力？这是待验证的设计主张。当前项目提供可试用协议和评估办法，没有提供支持普遍效果的真实样本。

“AI 生成得更好”和“学习者学得更好”应分开观察。AI 做出了合格产物，可以说明协作完成了任务；若学习者不能解释关键决策或应对新变化，不能据此宣布掌握。

## 从 1.0.0 到 1.1.0 的补充

| 原有不足 | 本次补充 | 为什么影响使用 |
|---|---|---|
| 产物验证与独立能力区分不够显式 | 目标侧重、成果线与能力线分别记录 | 避免把协作成果当成个人能力 |
| 未系统记录提示依赖 | 独立、提示后、跟随示范、AI代做 | 同样答对可能代表不同能力 |
| 主要关注即时表现 | 可选的延迟新题复测 | 记录隔一段时间后的表现 |
| 模拟迁移与L4关系不够明确 | L4要求已有真实实践证据；模拟单独标记 | 防止纸面答题被升级为真实能力 |
| “复述并应用”可能一轮出两题 | 每轮选一种，后续再补另一类证据 | 保持一问一答 |
| 每轮记录容易变成每轮输出大表 | 对话中维护，阶段结束或中断时导出 | 减少重复内容 |
| 固定地图大小易导致凑数 | 简单任务可压缩到2–3块 | 保留必要背景，控制范围 |
| 名称可能误触发介绍或编辑请求 | 明确方法介绍、skill编辑的路由 | 用户修改项目时不被拉入教学 |
| 展示材料不足 | README、完整虚构案例、评估模板 | 访客能理解、试用、反馈 |

Frontmatter 的兼容性描述保留在 metadata 中，以适配本地校验器允许的字段；这不表示原先顶层 `compatibility` 一定违反其他客户端的规范。

## 三类验证不要混用

1. **文件验证**：元信息能否解析，引用文件是否存在，分发目录是否完整。通过只说明包结构可用。
2. **协议验证**：在真实 AI 会话中运行验收场景，观察教学节奏、证据判断与路由。用例已经写好，不代表已经执行通过。
3. **学习效果验证**：由真实学习者完成任务、新题与延迟测试。演示对话和模型自我评价不能替代这一层。

记录模板位于 [evaluation-record.md](../skills/vista-learning/tests/evaluation-record.md)。一次测试记录客户端、模型（可见时）、版本、输入、输出、帮助程度和判定理由。若测试要求多轮，用同一会话保留相关上下文；独立场景则用新会话。

## 一次小规模试用如何做

选择有明确产物、错误代价低的任务，例如清洗匿名练习数据。先约定验收项和允许的资料/工具，再完成一道简短前测。按 VISTA 练习后，用难度相近但不同的新题检查，并在后续会话做延迟复测。

建议记录：

| 观察项 | 记录方式 |
|---|---|
| 成果质量 | 事先约定的标准及未达标项 |
| 独立应用 | 未见题的回答、推理与错误 |
| 帮助依赖 | 提示次数及关键提示内容 |
| 时间成本 | 主动学习、执行、等待分别记录 |
| 延迟表现 | 间隔、工具条件与新题结果 |
| 迁移边界 | 换场景后能否指出适用与失效条件 |

初次可以只收集一个完整案例，用来发现协议问题。若要比较其他学习方式，需要可比任务、工具条件与评价规则，并记录顺序、基础差异等干扰；不要把一人一次前后变化归因于 VISTA。

## 有意保留的边界

- 对兴趣探索，允许先探索再形成任务；不要求所有学习都对应工作绩效。
- 对系统性理论学习，需周期性回看领域地图和前置知识，防止只补眼前缺口。
- 对一次性交付，允许直接借助工具；用户要求培养独立能力时才追踪相应能力。
- 对技能熟练度与长期保持，一次对话能提供的证据有限；没有后续数据就保留待验证。
- 延迟复测的时间建议只是任务安排，不宣称最佳学习间隔，也不会自动创建提醒。
- 案例中的材料是练习输入，其中夹带的指令不改变用户的教学目标或助手的权限。

## 下一份最有价值的证据

一份经过学习者同意公开、完成匿名处理的真实学习记录：开始时的错误、接受了什么帮助、实际产物、新题表现、延迟结果。它比增加一套新的阶段名称更有助于判断方法是否需要调整。
